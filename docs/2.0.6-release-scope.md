# IDC Skills Forge 2.0.6 release scope

2.0.6 is a security-patch candidate for the same **limited-trust, public
content-authenticated profile** as 2.0.5. At builder handoff it is unsigned and
unpublished. This document defines the intended claim and promotion gates; it
is not evidence that those gates have passed. No skill is swapped or added.

## What changed from 2.0.5

- K3-205-008: review/publication Git helpers share the hardened runner, suppress
  fsmonitor/hooks and reject executable filters and diff drivers before use.
  The source freshness launcher pins the repaired trust-module bytes.
- K3-205-009: absent public commit objects fail strict validation; the three
  legacy critiques are explicitly staging-only history, not release acceptance.
- K3-205-010: platform records require bounded captured artifacts whose hashes,
  exact candidate, command, environment, status and output agree. Consistency
  is not a signature or proof of actual host/platform execution.
- K3-205-003/004/005/006: repair editor and transport program classification,
  compound-position strict checks and exponential assignment parsing. Preserve
  normal message, literal-argument and fetch controls plus the strict byte ceiling.
- K3-205-007: bounded browser observation retains interception through confirmed
  target termination, re-probes after settling and refuses child-frame contexts.
  Output records configured and actual bounds; it never claims lifetime containment.
- K3-205-026/027/031: annotate staging-only citations, bind publication tags to
  committed registry bytes, and keep generated bytecode from breaking canonical
  validation without relaxing signed inventory checks.
- Intended release-control values are release `2.0.6`, `manifestSequence` 5.
  Manifest/signature regeneration, fresh independent acceptance and versioned
  witnesses are required for the successor; none is borrowed from 2.0.5.

The source register's severity/status values remain intact. Construction repairs
are pending independent certification; 001/002 mechanisms and the remaining
out-of-scope backlog are not silently closed. Related 015/017 regression coverage
does not confer a blanket finding disposition. Full detail and red/green fixtures:
[`CHANGES.md`](../ops/mission/evidence/2.0.6/CHANGES.md).

## Intended scoped claim after promotion

The owner-held Forge content key signs a canonical manifest binding the exact
tracked release bytes and POSIX mode intent for all 50 skills and control files.
Consumers compare the full fingerprint and version-specific identity across
GitHub, company HTTPS JSON and DNSSEC before trusting repository code. The tag,
commit, tree, manifest digest and fingerprint must agree; additionally compare
the signature digest between GitHub assets and HTTPS JSON (DNS does not carry it).

Repository and browser results prove only their exercised cases and time bounds.
The guard is a bounded classifier, not a shell sandbox. Browser interception is
not packet-level ICE capture or proof for arbitrary future timers/interactions.
Concurrent hostile same-UID mutation, trusted-runtime compromise and independent
reviewer/runner identity remain separate trust assumptions.

## What 2.0.6 does not claim

- production 2-of-3 root or release-role custody;
- multi-party signer withholding or root-rotation resilience in live custody;
- completion of the deferred full two-receipt/eleven-lane acceptance ceremony;
- independent Windows/NTFS/OpenSSH platform acceptance;
- freshness-authorized four-root fleet parity;
- a disjoint publication-observer attestation;
- universal behavior across every harness surface; or
- the full external-threshold result `readyToRun=true`.

Fixing 008/009/010 is a prerequisite for stronger activation, not that ceremony.
The stronger publication verifier remains outside this scoped promotion gate.
No immutable 2.0.5 tag, signature, witness or acceptance packet is altered.

## Promotion gates

Before publishing the 2.0.6 tag:

1. Independently certify the repaired source at its exact local commit/tree and
   reconcile each changed ID and retained residual. Codex is the builder, not an
   independent acceptance-receipt seat.
2. Finalize approved content, release framing and inventory; run the full tests,
   matrices, canonical/Forge-50 checks and clean-clone QA.
3. Owner generates the canonical manifest, then biometrically signs as the last
   tracked-byte mutation. Commit that signed state and verify the exact identity.
4. Require protected CI and fresh Kimi independent acceptance at the final
   candidate, **before publication**. Any content/tree move voids prior acceptance;
   a changed commit also requires review identities to be reconciled explicitly.
5. Publish new version-specific HTTPS and DNSSEC witnesses, keeping prior records
   intact. Compare every bound value with the signed candidate and release assets.
6. Publish the immutable annotated tag and exact assets only after acceptance;
   re-read GitHub and both witnesses. Stop on mismatch.

Fleet rollout is a later owner-authorized step with installation/parity checks.
None of these external actions was performed by the local patch builder.
